# Accessibility Instructions

These instructions apply to all interactive UI components and automation components. Target: **WCAG 2.1 AA**, plus WCAG 2.2 § 2.5.8 for pointer target size (§ 7) — 2.1 has no target-size criterion at AA level. The primary focus is **keyboard navigation** — every new interactive component must be fully operable without a mouse.

Display-only SVG instruments (navigation-instruments, building-blocks, bars-graphs) are out of scope unless they expose interactive affordances (e.g. draggable setpoints).

## 1. Follow the WAI-ARIA Authoring Practices

Keyboard behaviour rarely needs to be designed from scratch. Before writing a key handler, look the widget up in the [WAI-ARIA Authoring Practices Guide (APG) patterns](https://www.w3.org/WAI/ARIA/apg/patterns/) — it is the industry-standard reference for how each widget type is expected to behave, and it is what keyboard and screen-reader users have already learned from every other application. A component that invents its own bindings is usually harder to use, not more discoverable.

This section is guidance, not a conformance checklist: it describes the default worth starting from, and it assumes you will exercise judgement. Work down the ladder and stop at the first step that applies:

1. **An APG pattern matches the widget.** Follow it — its roles, its states, and its keyboard interaction table — as closely as the component allows. Leaving out part of a pattern is a normal call to make (some behaviours the APG lists are optional, others are not worth the complexity for a given component); just note what you left out in the implementation's JSDoc, so an intentional gap doesn't read as a bug.
2. **No exact match, but a close one exists.** Adapt the closest pattern rather than starting over, and keep its key bindings for the parts that do map. Say which pattern you adapted and where the component departs from it.
3. **Nothing in the APG applies.** Design a pattern, then write it down in the component's JSDoc and the PR body. A home-grown pattern should still reuse conventional keys with their conventional meanings (`Enter`/`Space` activate, `Escape` cancels or backs out, arrow keys move within a composite widget), avoid overriding keys the browser or assistive technology owns, expose its state through ARIA so it is announced rather than only visible, and never leave the user stuck in a keyboard trap.

Link the pattern you followed from the implementation so the next reader can check the code against the spec. The tree navigation components are the reference example of step 1, spread across three files: [`tree-navigation.ts`](../../packages/openbridge-webcomponents/src/components/tree-navigation/tree-navigation.ts) renders `role="tree"`, [`tree-navigation-item.ts`](../../packages/openbridge-webcomponents/src/components/tree-navigation-item/tree-navigation-item.ts) renders `role="treeitem"` and handles activation, and [`TreeRovingNavigator`](../../packages/openbridge-webcomponents/src/internal/tree-roving-navigator.ts) contributes the navigation half — roving tabindex plus Up/Down, Left/Right and Home/End — linking the [Tree View pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/) from its JSDoc and stating that type-ahead and `*` are intentionally out of scope.

Step 3 is rare, but it comes up where a maritime interaction has no desktop-widget equivalent. `obc-slide-button` ([issue #1070](https://github.com/Ocean-Industries-Concept-Lab/openbridge-webcomponents/issues/1070)) is the open example: slide-to-confirm exists to force a deliberate action, and no APG pattern covers it, so the keyboard equivalent has to be designed rather than borrowed — say, `Enter` or `Space` to arm and the same key again to confirm, with `Escape` to disarm, keeping both activation keys working as § 2 expects. The specifics belong to that issue; the point here is that the resulting pattern gets written down. Departing from the APG because a domain constraint calls for it is fine; departing from it without noticing is what this section is meant to prevent.

## 2. Keyboard Navigation

Every interactive element must be reachable and operable with the keyboard alone.

### Reachability

- Prefer native focusable elements (`<button>`, `<a>`, `<input>`, `<select>`, `<textarea>`) inside the component's shadow DOM for their focus, activation, and semantic behavior.
- **Do not silently swap a non-native element for a native one in an existing component.** Changing a `<div>` wrapper to a `<button>` can break layout, event bubbling, form submission, ARIA overrides, and visual regression snapshots. If a component currently uses a non-native element and would benefit from a native one, **propose the change and wait for user confirmation** before implementing it.
- When the component's host element itself is the interactive target (no native element inside), make the host focusable by setting `tabindex="0"` on the outer touch-target wrapper — not on `:host` directly, so parent components can still override tab order.
- Never put `tabindex` values greater than `0`. Use DOM order to control tab sequence.
- A `disabled` interactive component must be removed from the tab order (native elements do this automatically; for custom wrappers use `tabindex="-1"` when `disabled`).

### Activation keys

| Element                                                                            | Keys that must activate                                                                                                                             |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Button, toggle                                                                     | `Enter` and `Space`                                                                                                                                 |
| Checkbox                                                                           | `Space` only (per WAI-ARIA APG — `Enter` is not part of the checkbox pattern)                                                                       |
| Link                                                                               | `Enter` only                                                                                                                                        |
| Radio group                                                                        | Arrow keys move focus **and** change selection in one step; `Space` checks a focused-but-unchecked radio (edge case, e.g. when nested in a toolbar) |
| Tabs — manual activation (default)                                                 | Arrow keys move focus between tabs; `Enter` or `Space` activates the focused tab and shows its panel                                                |
| Tabs — automatic activation (only when panels preload with no perceptible latency) | Arrow keys move focus and activate the panel simultaneously                                                                                         |
| Menu / dropdown                                                                    | Arrow keys to move, `Enter` to select, `Escape` to close                                                                                            |
| Slider, stepper                                                                    | Arrow keys to change value, `Home`/`End` for extremes                                                                                               |
| Modal, dialog, overlay                                                             | `Escape` to dismiss                                                                                                                                 |

Tab activation defaults to **manual**. Only switch to automatic activation when every tab panel's content is already loaded in the DOM and there is no user-perceptible latency on activation — otherwise automatic activation slows keyboard users who are just trying to traverse the tab list. Follow the [APG tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) for the full specification.

Pattern for custom activation handlers:

```ts
private handleKeydown(event: KeyboardEvent) {
  if (event.key === 'Enter' || event.key === ' ') {
    event.preventDefault();
    this.activate();
  }
}
```

### Composite widgets

Groups of related controls (tab groups, radio groups, menus, toolbars, trees) use a single tab stop with arrow-key navigation inside the group — not one tab stop per item. Follow the APG pattern for the widget type (§ 1); `TreeRovingNavigator` in [`src/internal/tree-roving-navigator.ts`](../../packages/openbridge-webcomponents/src/internal/tree-roving-navigator.ts) is a reusable implementation of the roving-tabindex mechanics for tree hosts.

### Focus trapping

- Do **not** trap focus in normal components.
- Modal dialogs **must** trap focus while open and restore focus to the invoking element on close.
- `Escape` must close the modal.

## 3. Focus Indication

- The `@mixin style` already renders a `:focus-visible` ring across all six interaction states. Do not override or disable it.
- Never write `outline: none` without providing a visible replacement of equal or better prominence.
- The focus ring belongs on the **touch-target** layer (outer wrapper), not the visible wrapper — this matches the two-layer DOM convention described in `AGENTS.md` § 7.
- Verify the ring is visible in all four themes (`day`, `dusk`, `night`, `bright`) before merging.

## 4. ARIA & Semantics

- If a native element does the job, use it; don't reach for `role=` when `<button>` works.
- Custom wrappers that act as a button/checkbox/etc. must declare a matching `role` and mirror the relevant state attributes:

  | State                  | Attribute                                                 |
  | ---------------------- | --------------------------------------------------------- |
  | Pressed toggle         | `aria-pressed="true\|false"`                              |
  | Expanded disclosure    | `aria-expanded="true\|false"`                             |
  | Selected tab/option    | `aria-selected="true\|false"`                             |
  | Checked checkbox/radio | `aria-checked="true\|false\|mixed"`                       |
  | Disabled               | `aria-disabled="true"` **or** native `disabled` attribute |
  | Current page/step      | `aria-current="page\|step\|…"`                            |

- Interactive components without visible text need `aria-label` or `aria-labelledby`. Icon-only buttons fall in this category.
- Alert/alarm surfaces should use `role="alert"` or an `aria-live` region so screen readers announce state changes.
- Grouped controls need a group label: `aria-labelledby` pointing at a heading, or `aria-label` on the group element.

## 5. Disabled vs `aria-disabled`

- `disabled` (HTML attribute) — removes the element from the tab order and disables activation. Preferred for buttons and form controls.
- `aria-disabled="true"` — keeps the element in the tab order but announces it as unavailable. Use only when the element must remain focusable (e.g. a disabled item that still shows a tooltip explaining why).
- The existing `disabled` boolean property on components should map to the HTML attribute unless a design reason dictates otherwise.

## 6. Color & Contrast

- **Never hardcode colors or guess contrast values.** The correct palette tokens live in Figma and are mirrored in `src/palettes/variables.css`.
- Use the existing CSS variables for all backgrounds, borders, text, and icons. If a needed token is missing, ask the designer — do not invent a fallback hex.
- Four themes (`day`, `dusk`, `night`, `bright`) are already contrast-checked. Custom color choices bypass this guarantee.
- Icon and text colors follow the `--on-{variant}-{role}-color` convention; use `active`, `neutral`, or `disabled` roles as defined in `AGENTS.md` § 7.

## 7. Touch & Pointer Target Size

The floor every interactive component **must meet** is WCAG 2.2 **[2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)**: every pointer target at least **24 × 24 CSS px** (exceptions: spacing, equivalent control, inline text, user-agent default, essential). The standard way to clear it — with margin — is the two-layer touch/visual pattern ([IMPLEMENTATION_GUIDELINES.md § Component Layout Architecture](../../IMPLEMENTATION_GUIDELINES.md#component-layout-architecture)): a transparent outer touch target of `--global-size-spacing-touch-target-min` — **48 px** at `regular`, the smallest size class (56 / 72 / 96 px at medium / large / xl), which also satisfies the stricter AAA criterion 2.5.5 (44 px). A few existing components fall short of the pattern (e.g. `obc-transmitter-button`'s tightly-sized native button); treat those as defects to bring into line when touched, not as precedent.

Rules when building or changing components:

- Size the hit area from the component's `-touch-target-size` token (which aliases the global minimum), never a raw px value. No property, variant, or size class may take an interactive target below 24 CSS px — and nothing should go below the 48 px token without a designer decision recorded in the JSDoc.
- The touch target is the invisible outer wrapper, not the visible surface (a slider thumb draws 12 × 28 but hits 48 × 48). The focus ring lives on that outer layer (§ 3).
- **SVG glyphs are not touch targets by themselves.** Instrument decorations like the setpoint marker (26 × 21 SVG units) scale with the instrument's viewBox, not with the size-class tokens — under `fixedAspectRatioScaling` they render _smaller_ than designed (~17 × 14 px at gauge-trend's default height). The shipped setpoint is display-only; if any SVG affordance is ever made draggable/clickable, give it an explicit invisible hit shape (`pointer-events` rect/circle) that stays ≥ 24 CSS px at the smallest supported rendering, and state that size in the story.
- Scrollbars: the default (`*`) profile is the 12 px **thin** one — acceptable for wheel/trackpad, below the floor for touch dragging. Surfaces meant to be scrolled by touch opt into `.obc-normal-scrollbar` (24 px) or `.obc-wide-scrollbar` (48 px) from `src/main.css`.

### The units these guarantees live in

All sizes are **CSS px**, and they only hold if the page does not scale them away:

- Any page hosting the components on a phone or tablet must declare `<meta name="viewport" content="width=device-width, initial-scale=1" />`. Without it, mobile browsers lay out at ~980 px and shrink to fit, rendering a nominal 48 px target at ~19 effective px on a 390 px-wide phone — below the WCAG floor. This is a prerequisite, not a tuning knob: do not use other `initial-scale` values to resize the UI (desktop browsers ignore the viewport meta; pinch-zoom overrides it) — pick a size class instead.
- Physical-size regimes are a **deployment** concern, not a component one. Type-approved maritime equipment (IEC 62288, which points to IEC 60945) requires a 15 mm minimum touch target; 15 mm ÷ 48 px = **0.3125 mm per CSS px**, so a compliant installation calibrates each screen (OS display scaling or browser zoom on known hardware) so one CSS px renders at ≥ 0.3125 mm — or uses a larger size class. The components stay in CSS px and enforce only the WCAG floor; IEC numbers belong to the design guideline and the integration, never to component code.

## 8. Testing Checklist

Before marking an interactive component as done:

1. **Pattern check** — the interaction matches the APG pattern named in the component's JSDoc, and anything left out of that pattern is noted there. A home-grown pattern belongs in the PR body too (§ 1).
2. **Tab through** the component in a story — every interactive element receives focus in a sensible order.
3. **Activate with keyboard only** — `Enter`, `Space`, arrow keys and `Escape` behave per the table in § 2, plus any keys specific to the component's pattern (`Home`/`End` and Left/Right for a tree, for example).
4. **Focus ring** is visible in all four themes.
5. **Screen-reader smoke test** — run NVDA (Windows), VoiceOver (macOS), or Orca (Linux) and confirm the component announces its role, label, and state.
6. **Disabled state** is skipped by `Tab` (unless deliberately using `aria-disabled`).
7. **Modal focus trap** (if applicable) — `Tab` cycles within the modal; `Escape` closes and returns focus to the invoker.
8. **Target size** — every pointer target is ≥ 24 × 24 CSS px (§ 7); the standard tokens deliver 48 px+. Check the `regular` size class, every variant, and — for anything SVG-interactive — the smallest story size.
